# Supabase

Schema, migrations, generated types, RLS, database tests, and the service-role allowlist.

Read `docs/vendor/supabase/declarative-database-schemas.md`, `generating-types.md`, and `testing-overview.md` before touching anything in `supabase/`. Load the `supabase-postgres-best-practices` skill before writing SQL.

## Projects and environments

| Environment | Database | Used by |
|---|---|---|
| `development` (local) | `supabase start` (Docker) | `npm run dev` |
| `development` (cloud) | cloud project `the-social-house-development` | `develop` branch deploy, deploy previews |
| `production` | cloud project `the-social-house-production` | `main` |

Migrations reach cloud projects **only** through GitHub Actions on merge (`supabase db push`, then `supabase config push`). Never run `supabase db push` or `supabase config push` from a laptop, never change schema or auth settings in the dashboard or SQL editor. Anything done there is invisible to `db diff` and gets overwritten.

## Schema workflow (declarative)

1. Edit `supabase/schemas/*.sql` — one file per table or concern (`companies.sql`, `rooms.sql`, `bookings.sql`, `outbound_emails.sql`, `policies/*.sql`, `functions/*.sql`). `./schemas` is discovered by default; ordering needs no config (the generated migration lists tables alphabetically with FKs as trailing `ALTER TABLE … ADD CONSTRAINT`).
2. `supabase db schema declarative sync --name <short_name> --no-apply` → a migration in `supabase/migrations/`. Read the generated SQL before committing. (Since CLI 2.116, `db diff` no longer reads `supabase/schemas/`; it only compares migrations with a database.)
3. `supabase db reset` locally, then `npm run db:types`, then `supabase test db`.
4. Commit schema file, migration, and regenerated types together.

Things declarative schemas **cannot** express go in a hand-written migration (`supabase migration new <name>`): DML (seed-like inserts, backfills), `alter policy`, grants on views, `security invoker` on views, comments, `create domain`, partitions, publications. Append new columns at the end of a table to keep diffs clean.

## Naming and types

- Tables plural, snake_case. **Every column is prefixed with the singular table name** (ADR-0018): `booking_id`, `booking_start_at`, `booking_room_id`. Referenced PKs keep their own prefix (`room_id`).
- Money: integer øre, `_ore` suffix (ADR-0019). Excl. VAT always (ADR-0020).
- Time: `timestamptz` in UTC; opening hours as `time` in `Europe/Copenhagen` (ADR-0021).
- Identifiers lowercase; `uuid` PKs via `gen_random_uuid()`; `created_at` / `updated_at` with the table prefix.
- Enums as Postgres `enum` types named `<table>_<column>` (e.g. `booking_status`, `booking_invoicing_status`).

## What lives in Postgres

Integrity that must hold regardless of which code path writes:

- **No overlap**: exclusion constraint on `bookings (booking_room_id, tstzrange(booking_start_at, booking_end_at + buffer))` for non-cancelled, non-expired rows, including the 30-minute buffer (ADR-0002). House Events participate in the same constraint.
- **Snapshot immutability**: price snapshot columns (ADR-0005) cannot change once `booking_status = 'confirmed'` — trigger raises.
- **Booking number**: generated by a sequence-backed function, never by application code.
- **Holds**: `booking_status = 'pending_verification'` rows with `booking_hold_expires_at`; availability queries and the exclusion constraint ignore expired holds.

Price, discount, fee, buffer-window, and opening-hours **arithmetic** lives in `lib/domain/` (TypeScript, Vitest), not in SQL. Postgres verifies; TypeScript computes.

## Generated types

`lib/supabase/database.types.ts` is generated, committed, and checked in CI (`supabase gen types typescript --local` must match). Regenerate with `npm run db:types` after every schema change. Never hand-edit. Import `Database` from there for every client.

## Clients

| File | Key | Use |
|---|---|---|
| `lib/supabase/server.ts` | publishable + user cookies | Server components, server actions. Default choice. |
| `lib/supabase/client.ts` | publishable | Client components only when unavoidable (realtime, optimistic UI). |
| `lib/supabase/admin.ts` | secret (service role), `import "server-only"` | Allowlist below only. |

RLS is the security boundary. Admins are ordinary authenticated users whose JWT carries `app_role = 'admin'` (see `auth.md`); write admin policies as `(auth.jwt() ->> 'app_role') = 'admin'` so admin screens use the normal server client.

## Service-role allowlist

The service-role client may be imported in exactly these places. Adding a sixth requires updating this list in the same PR.

1. The `/login` server action — resolve `company_username` → auth email before `signInWithPassword`.
2. Verification-code flow and booker-facing booking pages — the booker is not an auth user (ADR-0004).
3. Cancellation via secure link — unauthenticated.
4. `lib/email/sendMail.ts` and the Resend webhook — `outbound_emails` writes.
5. `supabase/functions/send-email` — the Auth Send Email Hook (Deno, uses its own env).

Everything else uses the user's session and RLS.

## Database tests (pgTAP)

`supabase/tests/*.sql`, run with `supabase test db` (locally and in CI). Every RLS policy and every constraint/trigger listed under "What lives in Postgres" has a test. Pattern: `begin; select plan(n); ... select * from finish(); rollback;`, simulate users with `set local role authenticated; set local request.jwt.claim.sub = '<uuid>';` and admins by also setting the `app_role` claim. Name files `NNN_<rule>.sql` grouped by suite number (`100` RLS, `200` integrity); each file owns its fixtures inline. See `docs/vendor/supabase/testing-overview.md` and `testing-pgtap-extended.md`.

## Seed

`supabase/seed.sql` runs on `supabase db reset` only: one admin, two rooms with opening hours and add-ons, one member company, one external company. It never runs against cloud projects; cloud admins are created with `scripts/create-admin.ts`.

## Auth config as code

`supabase/config.toml` is the source of truth for Auth: `enable_signup = false` (ADR-0008), Send Email Hook and Custom Access Token Hook enabled, built-in email templates unused, OTP and session lifetimes. Pushed by CI with `supabase config push`. Dashboard changes are forbidden.
